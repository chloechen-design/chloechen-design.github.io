# FTL WMS 与仓储产品设计系统

> 文档状态：基于现有法文项目材料的事实整理稿  
> 语言状态：中文事实源；公开案例使用英文并忠于本文件  
> 日期：2021–2022（原案例封面所示）

## 项目概览

FTL 已有内部 WMS，但原有系统存在可用性与维护方面的限制。项目一方面改进 WMS 与 PDA 等仓储工作界面，另一方面建立可以支持后续演进的内部 Design System / UI Kit。

- **我的职位**：UX/UI Designer
- **工作内容**：用户需求分析、既有系统 UX 审计、路线与优先级规划、内部协作、WMS 页面设计、PDA 界面优化、Design System 与 UI Kit、高保真原型、用户测试/原型调整以及交付协作。
- **协作对象**：产品、设计、PO/Scrum Master、开发、运营与物流负责人、仓库一线用户。
- **工具**：Figma、Jira、Miro、Notion、Storybook、Webflow（内部 release notes）。

## 现有材料中可以确认的研究与工作

1. 访谈材料覆盖一线仓库人员、经理/运营以及产品/开发相关角色。
2. 内部 WMS 问卷用于了解使用习惯、困难、未满足期待和后续改善方向；原材料没有可靠展示样本总数。
3. 项目进行了现有 WMS 的 UX/ergonomic audit。审计记录了导航结构、标签和图标识别、按钮/标签语义不一致、错误信息不够清晰等问题。
4. 项目材料展示了从用户原话（Verbatim）到用户需要（Need）再到产品要求（Requirement）的综合方法，并包含用户画像、journey / pain points、优先级和 roadmap 相关交付。
5. 原材料描述了团队在关键原型上进行用户测试与迭代，以及与 PO/开发进行功能评审。
6. 交付物包含 Figma Design System / UI Kit、WMS 高保真界面、PDA 界面工作、Storybook 交互组件文档、Jira 模板、Help Center 和内部 release note。

## 有据可引的调研例子

内部 WMS 问卷有一条反馈称，用户如果频繁使用，整体界面是直观的。可将其作为“熟练使用会弥补界面学习成本”的研究线索，但不能将单条反馈说成普遍结论。案例展示 Verbatim → Need → Requirement 时应标注这是一个追踪示例，不表示单一反馈独立决定了路线图。

当前系统审计还标记了：侧栏结构不清、标签过长、图标不易辨认、按钮与标签混用语义、错误弹窗使用技术语言且未充分解释后续动作。这些问题支持系统需要统一导航、命名、组件状态和反馈模式。

## Storytelling 建议

建议叙事顺序：内部 WMS 的可用性与维护问题 → 多角色访谈、内部问卷和 UX 审计 → 将反馈转换为可讨论的需求 → 为什么优先建立语义清晰、状态一致的组件基础 → Figma 库如何落到 WMS/PDA 界面 → Storybook、Jira、Help Center 与 release note 如何支持交付沟通 → 结果可证明什么、仍需什么数据验证。

## 证据边界

- 原材料中的流程图提及上线跟进、上线后满意度调查、维护移交等阶段，但现有证据不能单独证明每项计划都按图执行，也没有展示真实上线后的数据。
- 不使用未经证实的样本量、任务时间、满意度、实施错误下降、设计/开发提速或仓库生产率变化。
- Storybook 是技术团队基于共同组件工作建立的实现文档；不能称为设计师独立开发或维护。
- 可以确认作品集材料包含 Figma 库、系统化组件与状态、WMS/PDA 界面原型及交付沟通内容；成熟度和跨组织采用规模仍需进一步证据。
- “减少认知负担”“提高效率”“改善用户满意度”等只能作为设计目标或未来评估假设，不能写成项目结果。
